# 10 运维与成本

## 环境规划

| 环境 | 用途 | 配置 |
| --- | --- | --- |
| local | 本地开发 | Docker Compose，包含 PostgreSQL、MinIO、Redis |
| dev | 联调 | 单台服务器或开发虚拟机，Docker Compose |
| staging | 发布验证 | 单台服务器，使用独立数据和独立域名 |
| prod | 生产 | 单台高配服务器起步，后续拆分执行机或迁移 Kubernetes |

## CI/CD

流水线:

1. 代码检查。
2. 单元测试。
3. API contract test。
4. 数据库 migration check。
5. 构建 Web/API/Worker/Runtime 镜像。
6. 镜像漏洞扫描。
7. 部署到 dev。
8. staging e2e。
9. 人工批准后部署 prod。

执行镜像需要单独版本化，因为用户运行结果和运行环境相关。

## SLO 建议

| 服务 | 指标 | 初始目标 |
| --- | --- | --- |
| API | 可用性 | 99.5% |
| API | p95 响应时间 | 小于 500ms，排除长查询 |
| 调度 | 计划触发延迟 | p95 小于 60 秒 |
| 运行 | 状态更新延迟 | p95 小于 10 秒 |
| 报表 | 缓存报表打开时间 | p95 小于 3 秒 |
| 上传 | 100MB 文件上传后可预览 | 30 秒到 2 分钟，视推断队列 |

## 监控指标

控制平面:

- API QPS、错误率、延迟。
- 数据库连接池、慢查询。
- Redis 命中率和内存。
- Scheduler 扫描延迟、入队成功率、重试数。

执行平面:

- 运行容器创建失败率。
- 运行队列等待时间。
- 运行容器时长分布。
- OOM、timeout、cancel 数量。
- CPU、内存、临时存储使用。
- 每租户并发和用量。

产品指标:

- 首次上传成功率。
- 首次运行成功率。
- 定时任务创建数。
- 报表查看数。
- 报表订阅数。

## 告警

P0 告警:

- API 5xx 错误率超过阈值。
- PostgreSQL 不可用。
- Scheduler 停止心跳。
- Docker 守护进程不可用或运行容器创建连续失败。
- 对象存储不可用。
- 调度触发延迟持续超过阈值。

P1 告警:

- 某租户运行失败率异常升高。
- 单机 CPU、内存、磁盘或 Docker 容器资源不足。
- 日志写入失败。
- 邮件/Webhook 通知失败。
- 成本或运行量异常。

## 成本模型

主要成本:

- 控制平面常驻资源: Web、API、Scheduler、Worker、PostgreSQL、Redis。
- 执行计算: Docker 运行容器 CPU/内存。
- 对象存储: 上传文件、运行产物、快照、导出。
- ClickHouse: 运行日志、事件、大结果集。
- 网络出口: 报表导出、外部 API、对象存储下载。
- 通知: 邮件、Webhook、第三方集成。

成本控制:

- 当前 MVP 已提供工作区级数据源、项目、定时任务、报表数量、运行并发和数据源存储配额，Owner/Admin 修改会进入审计日志；运行/取消中的任务共同占用并发槽，满额任务保留在 queued 队列中。
- 终态失败的邮件/Webhook 投递会保留在控制台，管理员可在渠道仍启用时将原记录重入队，避免复制事件或绕过去重链路。
- 单次运行 CPU/内存/时长限制。
- 当前单机版提供 preview-first 的运行保留脚本：按终态运行 wall-clock 时间清除过期结果、日志、错误和运行目录，但保留运行元数据与审计。执行 `--force` 前应先备份。
- 当前保留脚本会删除过期历史报表快照，但始终保留每个报表的最新状态快照和最近成功快照；后续对象存储版本继续配置 bucket 生命周期和压缩策略。
- 失败任务退避重试。
- 打开报表默认读缓存，避免频繁实时查询。
- 当前 Owner/Admin 工作台按最近 24 小时、7 天和保留期展示运行数量、状态、成功率、计算小时、平均耗时与估算成本。设置 `ANYDATAS_RUNNER_COST_PER_HOUR_CNY` 后按运行 wall-clock 时长估算人民币成本；该值用于容量和预算趋势判断，不等同于供应商账单或精确 CPU 计量。
- 工作区运行检索页和 `/api/runs` 可按日志/错误关键词、状态、触发类型、项目及日期范围定位任务。默认每页 50 条、最大 100 条，结果只含 300 字符以内的匹配摘要；集中式 Loki/ClickHouse 日志库仍属于多机扩展阶段。

## 容量规划

MVP 初始假设:

- 10 个试点工作区。
- 每工作区 5 到 20 个用户。
- 每工作区 10 到 50 个项目。
- 每工作区 5 到 30 个定时任务。
- 并发运行总量 10 到 30。

单机初始限额可按工作区调整；新建工作区默认值由 `ANYDATAS_DEFAULT_MAX_DATA_SOURCES`、`ANYDATAS_DEFAULT_MAX_PROJECTS`、`ANYDATAS_DEFAULT_MAX_SCHEDULES`、`ANYDATAS_DEFAULT_MAX_REPORTS`、`ANYDATAS_DEFAULT_MAX_CONCURRENT_RUNS` 和以字节计的 `ANYDATAS_DEFAULT_MAX_STORAGE_BYTES` 控制。数据源存储默认 10 GiB，统计平台托管上传与 S3/MinIO 快照；XLSX 原文件和运行 CSV 均计入，重复路径只计一次。资源数量和存储配额防止元数据及磁盘无边界增长；工作区并发配额限制同时运行的脚本，CPU/内存仍由 Runner 配置负责。

扩容路径:

- API 横向扩容。
- Worker 横向扩容。
- Runner Worker 横向增加，或拆分到独立执行机。
- PostgreSQL 升级实例或读副本。
- ClickHouse 按日志和结果增长拆分存储策略。
- 对大客户独立服务器、独立 Docker network 或独立执行机。

## 备份与恢复

必须备份:

- PostgreSQL 元数据。
- 对象存储关键 bucket。
- Scheduler 状态和运行队列表，主要在 PostgreSQL/Redis。
- ClickHouse 审计和运行事件，按重要性设置 TTL。

恢复目标:

- 元数据 RPO 小于 24 小时，Beta 后小于 1 小时。
- 元数据 RTO 小于 4 小时，GA 后小于 1 小时。
- 对象存储误删通过版本控制或生命周期恢复。

## 常见故障预案

| 故障 | 处理 |
| --- | --- |
| 单机执行资源耗尽 | 暂停低优先级 schedule，降低并发或拆分独立执行机，提示用户排队 |
| 单个任务持续失败 | 自动暂停或降低频率，通知 owner |
| 数据源连接失败 | 标记数据源异常，阻止相关 schedule 继续重试风暴 |
| 对象存储写入失败 | 运行标记为 infrastructure_failed，可自动重试 |
| 报表快照损坏 | 回退到上一成功快照，提示刷新失败 |
| 数据库迁移失败 | 停止发布，回滚应用版本，按 migration 备份恢复 |
